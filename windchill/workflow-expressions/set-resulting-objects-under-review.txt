=====================================================================
 WORKFLOW EXPRESSION -- Change Activity
 Set all RESULTING objects to "Under Review", and surface the ones
 that cannot get there.
=====================================================================

READ THIS FIRST: WHERE ERRORS ACTUALLY APPEAR
---------------------------------------------
A workflow expression runs in the Method Server workflow thread. Most of the
time there is NO browser session attached to it. Throwing an exception does
not produce a popup unless the expression happens to be running inside the
user's own synchronous thread.

  Expression location                          Thrown error shows up as
  -------------------------------------------- --------------------------------
  Complete expression of a TASK node, when a    Red error banner in the user's
  user completes it from their Assignments      browser. The task stays open.
  -------------------------------------------- --------------------------------
  Robot node, Start expression, timer or        NOTHING in the browser. The
  transition fired with no user present         process goes into an exception
                                                state, visible in
                                                Process Administration, plus the
                                                process exception notification.
  -------------------------------------------- --------------------------------

So: use OPTION 2 if a user is completing a task. Use OPTION 3 if the node is
asynchronous -- it routes the failure to a task somebody can actually see.


WHERE THE EXPRESSION GOES
-------------------------
Workflow Template Editor -> Change Activity workflow template
  -> the Activity (or Robot) node
  -> right-click -> Properties -> Expressions tab -> Start / Complete

"primaryBusinessObject" is supplied by the engine and holds the WTChangeActivity2.


---------------------------------------------------------------------
 OPTION 1 -- SILENT. Promote what you can, log the rest, never block.
---------------------------------------------------------------------

ext.change.ChangeActivityStateUtil.promoteResultingObjects(primaryBusinessObject);


---------------------------------------------------------------------
 OPTION 2 -- LOUD. Throw so the user sees a red banner.
 Put this on the COMPLETE expression of the task the user completes.
---------------------------------------------------------------------

ext.change.ChangeActivityStateUtil.promoteResultingObjectsOrFail(primaryBusinessObject);


What the user sees (example):

    Change Activity CA-000123: 2 resulting object(s) could not be set to
    the "UNDERREVIEW" state.

      - 0000000456, A.1 : the "UNDERREVIEW" state is not available in the
        life cycle of this object
      - 0000000789, B.2 : the object is checked out and cannot change state

    Correct the objects listed above, then complete this task again.

The throw is a wt.util.WTRuntimeException -- UNCHECKED on purpose. The
expression box compiles your code into a generated method, and an unchecked
exception needs no throws clause, so this compiles wherever you paste it.

Objects that CAN be promoted still are, before the throw. The sweep is
best-effort; the exception only reports what was left behind.


---------------------------------------------------------------------
 OPTION 3 -- ROUTABLE. The correct design for a robot / async node.
 Capture the failure text, then branch the workflow on it.
---------------------------------------------------------------------

Step 1. In the workflow template, add a process variable:
            Name: failureReport      Type: java.lang.String

Step 2. Expression on the promotion node:

failureReport = ext.change.ChangeActivityStateUtil.promoteAndReport(primaryBusinessObject);

        Returns "" when everything worked, otherwise the same multi-line text
        shown under Option 2.

Step 3. Add a Conditional / Decision node straight after it, routing on:

failureReport.length() > 0

        TRUE  -> an assigned task, e.g. "Fix resulting objects", routed back to
                 the change originator or the Change Administrator.
        FALSE -> continue the normal happy path.

Step 4. In that task node, put ${failureReport} into the task Instructions.
        The user opening the task now sees exactly which objects failed and why,
        in a place they can act on -- which is what "show me an error on the UI"
        actually needs to mean for an asynchronous process.


---------------------------------------------------------------------
 HOW A FAILURE IS CLASSIFIED
---------------------------------------------------------------------
  Condition                                  Counted as   Reported to user
  ------------------------------------------ ------------ ----------------
  Promoted successfully                       promoted     no
  Already in Under Review                     skipped      no
  Not lifecycle managed at all                skipped      no  (user cannot fix)
  Checked out                                 FAILED       yes
  Lifecycle has no Under Review phase         FAILED       yes
  State-based access rule / gate vetoed it    FAILED       yes
  Target state undefined in StateRB           FAILED       yes (config error)
  Could not read the resulting objects        FAILED       yes

Honest limitation: "lifecycle has no Under Review phase" and "a gate vetoed
the transition" both arrive as WTPropertyVetoException and cannot be told
apart reliably from the exception alone. Both are reported with the same
wording. The Method Server log carries the underlying message if you need to
tell which one you hit -- grep for
"ext.change.ChangeActivityStateUtil".


---------------------------------------------------------------------
 MESSAGES ARE LOCALIZABLE
---------------------------------------------------------------------
All user-facing text lives in ext/change/changeResource.java as @RBEntry
annotations, not hardcoded in the logic. Two consequences:

  * Translations are added by adding changeResource_<locale>.java.
  * A site admin can reword any message WITHOUT a rebuild, via
    Site -> Utilities -> Resource Customization.

Reminder for when you edit the text: {0}, {1} are MessageFormat placeholders,
and a literal apostrophe must be doubled ('') or MessageFormat silently stops
substituting the rest of the line.


---------------------------------------------------------------------
 BUILD AND DEPLOY
---------------------------------------------------------------------
1. Copy both files into the Windchill source tree:
       <Windchill>/src/ext/change/ChangeActivityStateUtil.java
       <Windchill>/src/ext/change/changeResource.java

2. Compile:
       cd <Windchill>
       ant -f bin/tools.xml class -Dclass.includes="ext/change/**"

   Classes land in <Windchill>/codebase/ext/change/

3. Restart the Method Server.

4. Open the workflow template, paste the one-line expression, save, and set
   the template back to Released.

5. Test with a Change Activity that has at least one resulting object on a
   lifecycle WITHOUT an Under Review phase. If you cannot produce a failure
   on purpose, you have not tested the error path.


---------------------------------------------------------------------
 THINGS THAT WILL BITE YOU
---------------------------------------------------------------------
* "UNDERREVIEW" is the INTERNAL name. The display name "Under Review" will not
  resolve. Check yours in Site -> Utilities -> Enumeration Customization ->
  wt.lifecycle.StateRB.

* getChangeablesAfter() returns RESULTING objects. getChangeablesBefore()
  returns AFFECTED objects. Swapping them is the most common mistake here.

* Option 2 on a ROBOT node gives the user nothing and leaves the process in an
  exception state that somebody has to clear by hand in Process Administration.
  If the node is not user-completed, use Option 3.

* Objects are promoted in their own transactions, so a throw under Option 2
  does NOT roll back the objects that already succeeded. If you need
  all-or-nothing, move the Transaction outside the loop in promoteOne() and
  delete the inner catch -- and accept that one bad object blocks every good one.

* Better still, catch this before the workflow starts: a validator on the
  Change Activity submit action can refuse the submission with the same message
  while the user is still on the page. The workflow expression is the safety
  net, not the primary control.
